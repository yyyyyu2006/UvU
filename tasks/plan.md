## 1. 范围与技术选择

在现有“我的日历／角色日历”增加纪念日、生日、重要事项，复用现有日期格、编辑弹层、数据库保存队列、身份及备份入口。第一版不引入新日历框架、不新增运行时依赖，不迁移1900日期/回复基础路径。

| 能力 | 第一版建议 |
| --- | --- |
| 新建 | 选日期 → 添加重要日 → 名称、类别、日期、重复、颜色、备注 → 保存 |
| 类别 | 纪念日、生日、重要事项；普通日程保持原入口 |
| 日期 | 公历、全天单日；1900-01-01至2200-12-31，沿用现有校验范围 |
| 重复 | 不重复／每年；纪念日与生日预选每年，重要事项预选不重复，可手动切换 |
| 查看 | 月格小标记、当天详情置顶、紧凑“即将到来”列表 |
| 近期列表 | 从当前日历的今天起30天，含今天，按最近发生日排序；默认最多5条，可展开；不遍历生成所有年份 |
| 编辑和删除 | 重复记录明确“仅本次／此后所有／整个系列”；保留现有撤销及过时编辑拒绝 |
| 周年与倒数 | 今天／还有N天／已过去N天；可选显示第N周年，生日默认隐藏年龄；未来起始日期不显示负周年 |
| 聊天 | 每条记录允许引用 + 当前角色/存档共享开关均开启后才进入上下文 |
| 提醒 | 仅日历内的今天、近期和倒数显示；不新增后台通知或自动消息 |
| 后续扩展 | 农历、可靠后台提醒、跨设备同步、ICS互通另行确定范围 |

第一版完整日期必须由用户填写；关闭年龄/周年显示不表示年份未知。若用户只知道月日，先不伪造出生年或起始年，月日独立记录模式留作后续扩展。

## 4. 数据合同与旧数据兼容

沿用calendarData.events，并为新记录增加下列字段；旧普通记录缺字段时按旧日程解释，不凭标题猜类别。

| 字段 | 语义与默认 |
| --- | --- |
| kind | schedule / anniversary / birthday / important；旧记录缺失等于schedule |
| repeat | 旧取值保留；新重要日使用none或yearly |
| anchorDate | 原始纪念日日期，用于周年；普通日程不需要。本次改期不改变它 |
| yearlyMonthDay | 年度发生月日MM-DD，创建时取所选日期；与原始纪念日期、系列生效起点分开，避免非闰年拆分后将2/29永久改成2/28 |
| leapDayPolicy | 仅2/29年度记录用：leap-only（默认）/ feb28 / mar1 |
| showAnniversaryCount | 是否显示周年；生日默认false，其余由用户选择 |
| shareWithChat | 单条允许进入聊天上下文，默认false；普通日程不借此改变旧共享规则 |

新种类强制start=end、time=endTime为空，禁止通过导入绕开单日定义；anchorDate使用同样日期校验，yearlyMonthDay验证有效月日并允许02-29，相关布尔/枚举/长度在保存和导入时一致检查。保留id、owner、rev、source、until、except、locked、status原语义；不放开日期范围、记录数和导入体积限制。取消记录不出现在近期或聊天摘要；新重要日不提供“完成整个年度系列”，某次完成用例外和一次性派生记录处理，不能隐藏未来年份。

建议采用calendarData.version=2，明确宣布数据格式升级：

1. 新代码接受v1/v2；读取v1在内存提供缺省解释，单纯打开页面不写入数据库，也不升版本。
2. 未使用新功能的普通日程/心情等旧路径继续写v1；首次保存新类别、年度规则或新权限字段时，通过同一持久化事务写v2。写失败保持原库和界面状态，不落半个迁移。
3. 校验器与保存器支持已知两版；未来未知版本明确拒绝，不重置空库、不覆盖原数据；默认关闭的聊天路径仍只读profile小表，不遍历/克隆events，不因聊天触发迁移。
4. 迁移前提供日历备份入口及版本说明；完整v2导出必须保留年度规则、原始日期、例外和权限。新权限缺失一律关闭，不被旧日程共享授权代替。
5. 用户当前正式版仍用v1校验，不能直接导入v2。提供可选“兼容旧版导出”：选择一个目标年份，将该年有效年度实例变为一次性普通日程，保留原普通日程/心情/经期；明确列出转换数量、权限/类别/周年/其他年份等无法保留内容。取消/无有效实例的记录也要计入排除说明。
6. 兼容导出只生成文件，不改本库，普通ID不改、新派生ID唯一且合法；原始完整v2文件另外保留。回到旧代码前先保全当前完整v2备份，再恢复迁移前v1备份或用户已确认的兼容文件，不能只回Git版本就宣称数据已回退。

本合同的v2是应用内日历数据版本，不要求升级Dexie数据库结构；完整备份容器原格式继续保留。实现时需核验其他calendarData消费者，不能只改UI两个函数。

## 5. 日期与重复编辑规则

- 日期作为YYYY-MM-DD保存。今天按当前所选日历已有时区语义计算，环境时区未启用则用本机；切换时区只改变“今天”和倒数，不改变保存的纪念月日。
- 年度匹配yearlyMonthDay的月和日，start只作为系列生效下界，anchorDate用于周年；显式区分monthly/yearly，不把yearly放进现有月度兜底。拆分系列继承原yearlyMonthDay，只有用户明确改此后或全系列的年度日期才更新它。
- 2/29创建时显示非闰年策略：默认仅闰年，可选2/28或3/1。用1900、2000、2100及普通闰年验证公历规则；不用Date自动溢出决定策略。
- until按实际发生日含端点，except也记录实际发生日；跨年、2/29改期均遵守。只在可视范围生成临时实例，不每年写一份。
- 周年由发生年份与anchorDate年份计算；本次临时庆祝改期仍保留原始年份和月日。首次当年为0，不显示“负周年”；年龄显示由独立显隐控制。
- “仅本次”：原系列except加入原发生日，创建一次性实例并保留anchorDate/类别/权限；整个操作同一事务，失败不能只留下排除。
- “此后所有”：旧系列截到当前发生日前一天，新系列从选定发生位置开始；例外按新旧系列范围分配，原始纪念日期保持，除非用户明确改原始日期。
- “整个系列”：普通改标题/备注不改anchorDate；修改纪念日期会在编辑器明确显示影响范围，再统一更新规则。不能把当前查看的未来年份误写成原始起始年。
- 删除、撤销、跨窗口修改、切角色/存档期间保存均沿用rev和owner防护；相同姓名不同角色或存档不混写。
- 近期“未来30天”不代表计算下一次只看30天。下一发生日可按年份查找至2200边界，尊重例外/结束日期，遇到范围外显示“范围内无下次”，不无限循环。

## 6. 交互与展示

保留当前月历和日程/心情/经期切换。日程模式新增“添加重要日”入口，复用现有编辑器；常用项直接显示，闰日和聊天权限只在相关时出现，避免重复说明堆满表单。

月格用小色点/图标标记，详情列出完整名称；事件多时有数量提示，不挤压日期。选区、今天、节假日、心情和经期图层继续可见，重要日不用占满格子背景。色彩之外有类别文字/无障碍名称，不能只靠颜色区分。

当天重要日单独放在时间线前，普通定时行程保持原顺序。近期列表依据真实今天，不随用户查看历史日期变成“历史近期”；没有记录时提供紧凑创建入口。

沿用day watcher及visibility恢复刷新；页面再次可见、跨午夜、切换角色或存档后重新计算，关闭面板释放计时器/监听器。弹层内部滚动、焦点返回、键盘关闭与窄屏点击都在真实完整App检查。

CSS只增加css/modules/calendar.css内日历作用域选择器，兼容原版与自定义主题，不修改音乐、ID卡、已发送文件/邀请/日历卡片外观。

## 7. 聊天权限与AI排程隔离

两层许可，均默认关闭：

- 记录层shareWithChat：用户在该条重要日上允许被引用。
- 角色/当前存档profile：独立“引用角色重要日”“引用我的重要日”，拟用shareImportantDays / shareUserImportantDays。不由旧shareSchedule、shareUserSchedule推导，不能跨存档继承。

普通日程共享集合先排除新kind；重要日仅经上述两层权限收集。所有相关开关关闭立即返回，保留“不读取事件库、不添加上下文、不发额外请求”的原路径。实现使用显式上下文权限列表，不依赖FLAGS.slice的索引恰好对应某类开关。

建议只提供今天至未来7天、最多5条的摘要，按发生日排序，仅含标题/类别/日期和允许的倒数；默认不发备注、地点或隐藏年龄，摘要单独限长，并维持原日历总预算。若未来想让角色查询全部历史纪念日，需另定范围，不在第一版默认开放。

记录文本只作为日历事实数据，不能作为系统指令执行；沿用安全的纯文本构造。复用已有calendar.context入口及诊断，不改变1900提示词内容、历史范围、上下文顺序和回复顺序。

AI排程输入及冲突判断始终排除重要日；即使重要日解锁也不允许AI修改/删除。它只是不占时间的纪念标记；要安排庆祝时段，用户另建普通日程。生日不会使一天变成“全天忙碌”。

手动分享属于用户本次主动发送：提供预览，普通日程沿用原流程，重要日默认不选中，用户明确选择后才发；不暗中更改单条持续共享权限。已发送内容是消息快照，关闭共享或改日期不能承诺撤回过去消息，发送卡片渲染保持原样。
