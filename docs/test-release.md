# test 测试与 main 发布

- 正式站：https://yyyyyu2006.github.io/UvU/
- 测试站：https://yyyyyu2006.github.io/UvU/test/

后续修复先在 `test` 开发、自检、推送，再到测试站验收。用户确认没有问题后，才把测试通过的提交合并到 `main`；普通“推送”只更新 `test`。

## 自动部署

GitHub Pages 的来源设为 GitHub Actions。`.github/workflows/pages.yml` 在 `main` 或 `test` 推送后，分别读取两个分支的最新提交：`main` 放在站点根目录，`test` 放在 `/test/`。只有网站运行文件进入部署包，测试脚本、后端服务、仓库记录和 outputs 不公开。

两站的 `deployment.json` 给出实际部署分支、提交与打包时间。部署完成必须核对线上文件和页面，不能只看推送成功。流水线串行执行；部署失败时保留上一次成功版本。

## 测试数据

测试站第一次进入是独立空数据。可以在测试站手动导入备份，正式版和测试版不自动同步。正式版的网页源码、美化与数据名称保持原样。

部署时只给测试站添加存储命名空间：主数据库、音乐本地库、向量索引和语音缓存使用独立名称，localStorage/sessionStorage 使用独立键前缀，后台协作频道与锁也单独命名。测试版清理存储不会调用正式版键的清理。Service Worker、通知与安装入口位于测试路径。

两站仍在同一个 GitHub Pages 域名下，这属于应用数据隔离，不是浏览器安全域隔离；浏览器“清除此网站的所有数据”会同时清掉该域名下数据，浏览器通知权限也按域名共享。测试站不自动带入正式站的API密钥、账号与聊天记录，需要手动导入或配置。真实服务仍由原来配置决定。

## 自检与合并

本地修复仍按项目规则跑对应检查；发布前必须使用真实 `UVU_1900_ROOT` 运行 `npm test` 与 `npm run test:1900`，不能因云端没有原版目录而放宽为成功。当前自动部署只检查部署打包规则，不把它称为完整业务验收。

确认后先同步远端，检查 main/test 差异，合并经过确认的测试提交，再重复受影响检查与线上版本核验。保留提交历史，禁止强推覆盖正式分支。
