# 长按菜单遗漏和双语撤回显示 · 2026-11-17

## 范围与事实

- 起点为 test `1a35ab8cb94d7e0887a774ec7424bd46afe5e862`；本轮重新核验 Git `2.55.0.windows.5` 与远端 test/main 起点一致。
- 用户录屏中一处菜单只有“进入调试、多选、删除、从这里创建分支”，另一处具有编辑、引用等完整入口；消息看起来仍是普通双语气泡。
- 用户明确没有手动撤回，且不同用户使用不同美化也遇到过。不能把手动撤回或某套 CSS 写成已确认原因。
- 本轮确认下列两个可独立复现的问题；尚未取得录屏原消息的保存字段，不能证明录屏具体消息必然由其中某一条引起。不是全仓重新审查或全部遗留问题清零。

## 已确认问题与局部修复

### MSGMENU-20261117-01：菜单越出短屏

`js/ui.js` 的 `createContextMenu()` 使用开场缩放动画中的矩形测量高度；下方空间不足直接向上减去高度，没有限制上边界，也没有内部滚动。320×400、320×260 完整 App 中可复现负坐标，导致上方入口不可见。真实1900的同一函数已有该逻辑。

修复在原菜单内限制宽高、允许纵向滚动、按未缩放的布局尺寸计算，并限制上下左右边界。优先读 `visualViewport`（用户当前实际看到的网页区域），缺失时回退到 `innerWidth/innerHeight`；不重做菜单，不更改条目及主题文件。

### MSGMENU-20261117-02：双语渲染跳过撤回显示

`js/modules/chat_render.js` 的双语解析发生在撤回判断之前，正则也能匹配“撤回了一条消息：”。命中后提前返回普通气泡，而菜单按保存的 `isWithdrawn` 状态只给四项，引用被原规则禁止。真实1900也有同一顺序。

实际调用 `handleAiReplyContent()` 的角色自动撤回路径可在用户没有手动撤回时复现：两秒后字段变为撤回，界面仍像普通双语消息，菜单恰好四项。补丁仅让撤回消息跳过双语分支，回到已有撤回显示；不改变自动撤回规则、消息历史、引用权限或用户数据。正常消息仍可编辑和引用。

这是与录屏一致的已证实路径，但原消息是否真的经历自动撤回仍待确认。若 test 中未撤回的普通消息仍出现四项，需要进一步核对该条消息的脱敏 role/isWithdrawn/isThinking/isStatusUpdate/type 状态及实际菜单，不要求完整备份或密钥。
